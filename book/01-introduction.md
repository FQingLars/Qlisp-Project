# Глава 1. Введение

## 1.1 Что такое QLISP

**QLISP** — компилируемый диалект Лиспа, спроектированный специально для машинного обучения и AI. Три кита языка:

1. **Компиляция в нативный код.** Через LLVM и HLO-пайплайн (по мотивам XLA) ваши тензорные вычисления превращаются в машинный код с fusion-оптимизациями — без Python-интерпретатора в горячем цикле.
2. **ML — часть языка, не библиотека.** Тензоры, автоградиент, слои, оптимизаторы, классические алгоритмы ML, аудио-обработка — всё встроено в бинарник. Не нужен `pip install torch numpy sklearn`.
3. **Гомоиконность.** Код — это данные (S-выражения). Макросы, rule engine и паттерн-матчинг строятся на этом естественным образом.

```
Source → Reader → Macro Expand → Type Check → LLVM Codegen → Native Binary
                         ↓
                   Interpreter (dev/test)
                         ↓
                    LSP Server ←→ Editor
```

> 🐍 **Python-аналогия.** QLISP — это как если бы NumPy, PyTorch и scikit-learn были *встроены в интерпретатор* CPython, а вместо GIL был LLVM-компилятор, превращающий ваш код в машинный код.

## 1.2 Почему не Python

| Проблема Python в ML | Решение QLISP |
|---|---|
| GIL и медленный интерпретатор | Нативная компиляция через LLVM |
| GC-паузы на больших графах объектов | Region-based память без GC (гл. 5) |
| `torch.compile` — внешняя надстройка | HLO-компиляция — часть ядра языка (гл. 10) |
| Зависимости: `pip`, версии, окружения | Всё в одном бинарнике ~2 МБ |
| Декораторы/метаклассы — хрупкая метапрограмма | Настоящие макросы над S-выражениями (гл. 12) |
| Символьный AI (правила, унификация) — отдельные библиотеки | Rule engine и унификация в ядре (гл. 14) |

При этом QLISP не изолирует вас от Python-экосистемы: есть `LOAD-NPY`/`SAVE-NPY` для NumPy-массивов, JSON, CSV и FFI для вызова любых C-библиотек (гл. 16).

## 1.3 Философия языка

### Лисп-наследие

- **S-выражения** — единый синтаксис для кода и данных:
  ```lisp
  (+ 1 2)          ; это вызов функции → 3
  '(+ 1 2)         ; это данные: список из трёх элементов
  (eval '(+ 1 2))  ; данные можно исполнить → 3
  ```
- **Макросы** — функции, которые преобразуют код в код *до* исполнения. В Python ближайшая аналогия — декораторы, но макросы мощнее: они работают на уровне синтаксического дерева, а не объектов-функций.
- **REPL-first** разработка, как в Clojure и Common Lisp.

### ML-наследие

- **Тензоры первого класса.** `(tensor ((1.0 2.0) (3.0 4.0)))` — литерал, как `[ [1,2], [3,4] ]` в NumPy.
- **Автоградиент через ленту.** Операции с суффиксом `!` записываются на градиентную ленту, `(GRAD! loss)` — это `loss.backward()`.
- **Компиляция графов.** `(START-TRACE)` … `(HLO-COMPILE out)` — это `torch.compile()`: ваш код трассируется в граф, оптимизируется и компилируется в машинный код.

### Paper-memory

Уникальная модель памяти QLISP — «память на листке бумаги» (гл. 5). Всё, что вы вычисляете, — черновик: живёт в текущем scope и уничтожается при выходе. Сохранить можно только явным переписыванием «в тетрадь» — `defvar`. Никакого GC, никакого borrow-checker, никакого ручного `free`.

## 1.4 Где QLISP уместен

- **Обучение и инференс моделей**, где важна производительность нативного кода и отсутствие пауз GC.
- **Нейросимвольные системы**: экспертные правила + нейросети в одном рантайме, с общим автоградиентом (гл. 14, `NS-IF`).
- **Встраиваемые ML**: бинарник ~2 МБ без внешних зависимостей.
- **Быстрые прототипы алгоритмов ML** в REPL — с мгновенной перезагрузкой определений.
- **DSP/аудио**: FFT, STFT, mel-шкалы встроены (гл. 15).

## 1.5 Чего в QLISP нет (честно)

- Многопоточности общего назначения (тензорные ядра SIMD-параллелятся, BLAS — тоже, но пользовательских потоков нет).
- Богатой экосистемы пакетов — она только формируется (гл. 16).
- Unicode-строк в полной мере, отладчика с пошаговым исполнением.
