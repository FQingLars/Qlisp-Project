# Глава 5. Модель памяти: Paper-Memory

Модель памяти QLISP называется **paper-memory** («память на листке бумаги») — и это главная идея, отличающая QLISP и от Python (GC), и от Rust (borrow checker), и от C (malloc/free).

## 5.1 Аналогия с черновиком

Решая пример в столбик на бумаге, вы пишете исходные числа на черновике, промежуточный результат — тоже на черновике, и переписываете в чистовик только ответ. Черновик выбрасывается.

Paper-memory работает так же: данные по умолчанию **одноразовые** (disposable). Единственный способ сохранить — явный `clone`.

> 🐍 **Python-аналогия.** В Python всё живёт в heap, и garbage collector периодически находит и освобождает недостижимые объекты. Вы думаете о владении редко — платя GC-паузами и накладными расходами. В QLISP освобождение детерминированное и мгновенное: scope кончился — вся его память освободилась одной операцией.

## 5.2 Три правила

| Правило | Что означает | Аналогия |
|---|---|---|
| 1. Всё disposable | Данные живут в текущем scope, уничтожаются при выходе | Черновик |
| 2. Explicit save | `defvar`/`setq` глобального клонирует в immortal-память | Переписал в тетрадь |
| 3. No aliasing | Один владелец у каждого значения, нет shared-ссылок | Листок нельзя скопировать, можно только переписать |

## 5.3 Два мира данных

```text
┌─────────────────────────────┐     ┌─────────────────────────────┐
│  SCRATCH (disposable)        │     │  IMMORTAL (persistent)       │
│                              │     │                              │
│  let-биндинги                │     │  defvar/defun/defmacro       │
│  промежуточные SExpr         │     │  глобальные биндинги         │
│  временные списки            │     │  код-как-данные:             │
│  локальные замыкания         │     │    макросы, правила          │
│  деревья при макрораскрытии  │     │  plist-данные                │
│  forward/backward тензоры    │     │  веса модели                 │
│                              │     │                              │
│  Живёт 1 scope.              │     │  Живёт всю программу.        │
│  Уничтожается при выходе.    │     │  Никогда не сбрасывается.    │
└─────────────────────────────┘     └─────────────────────────────┘
```

Мост между мирами один: `clone`.

```text
scratch-значение ──[clone]──→ immortal-копия
```

> 🐍 **Python-аналогия.** Scratch ≈ локальные переменные функции, immortal ≈ глобальные переменные модуля. Но в Python переход «локальное → глобальное» — просто `global x; x = ...` со ссылкой; в QLISP это **копирование** значения в долгоживущую память.

## 5.4 Операции и их владение

| Операция | Входы | Выход | Где живёт |
|---|---|---|---|
| `(MATMUL x w)` | x потреблён, w нетронут | новый тензор | scratch |
| `(clone x)` | x нетронут | копия x | immortal |
| `(setq w val)` | — | — | обновляет `w` на месте |
| `(defvar w val)` | — | — | clone → immortal |
| `(defun f ...)` | — | — | clone замыкания → immortal |
| `(defmacro m ...)` | — | — | clone замыкания → immortal |
| `return` из функции | — | — | auto-clone в scope-родителя |

## 5.5 Почему это идеально для ML

Типичный цикл обучения:

```lisp
(while (< i 1000)
  (let ((pred (MATMUL! x w)))       ; pred ~1 МБ на scratch
    (let ((loss (MSE! pred y)))     ; loss ~1 байт, pred потреблён
      (GRAD! loss)                  ; градиенты на scratch
      (SGD-STEP w 0.01)             ; w обновлён на месте (immortal)
      (setq i (+ i 1)))))
```

1000 итераций используют **одни и те же ~1 МБ** scratch-памяти: без единого `free`, без GC-пауз, без роста потребления.

> 🐍 **Python-аналогия.** Это как если бы в PyTorch каждый `loss.backward()` не копил граф, а весь временный аллокационный мусор цикла исчезал мгновенно на каждой итерации — без `torch.no_grad()`-танцев и без allocator'а, который «иногда» решает освободить память.

## 5.6 Чего в QLISP нет

- `malloc/free` — нет ручного управления, нет фрагментации
- **GC** — нет обхода графа объектов, нет пауз, нет поколений
- **Reference counting** — нет счётчиков, нет проблем циклов
- **Borrow checker** — нет lifetime-аннотаций, нет `&mut` vs `&`
- **Views/aliasing** — нет shared-указателей на данные тензоров

## 5.7 Region-based реализация

Память устроена как дерево арен (arena = большой блок, из которого аллокации идут подряд):

```text
root_arena (immortal)
 ├─ REPL expr 1       ← дочерняя арена
 │   ├─ let bindings
 │   └─ fn calls
 ├─ while iter 1      ← дочерняя арена
 │   ├─ body evals
 │   └─ [уничтожена после итерации]
 ├─ while iter 2      ← новая дочерняя
 └─ REPL expr 2
```

- Каждый scope = дочерняя арена; аллокации идут в текущую (самую глубокую).
- Выход из scope — арена уничтожается целиком (одна операция, все объекты разом).
- `return` из функции — результат клонируется в родительскую арену.

Пулы буферов для тензоров (TensorBufferPool) переиспользуют память по размерам-бакетам, так что «создание» тензора в цикле обычно не затрагивает системный аллокатор.

## 5.8 Практические следствия

1. **Не держите «ссылки» из прошлого scope** — их нет и быть не может; сохраняйте значения через `defvar`.
2. **`(ARENA-STATS)`** — посмотреть статистику арен из REPL.
3. **Большие константы** (датасеты) объявляйте через `defvar` — они уйдут в immortal и переживут циклы.
4. Внутри горячего цикла — только `let`-биндинги и `!`-операции; это даёт нулевое накопление памяти.
